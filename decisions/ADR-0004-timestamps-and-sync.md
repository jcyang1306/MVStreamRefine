# ADR-0004: Timestamps, clock domains and robot pose synchronization
Status: Accepted. Date: 2026-10-27. Amended 2026-10-28 (decisions 3, 6, 8 from P1 measurements); the amendment was accepted by the owner the same day.

## Context
V1 stamped camera frames with `time.monotonic_ns()` after `wait_for_frames()` returned (exposure + transport + queue latency, typically tens of ms), polled the RM65 TCP pose at 50 Hz, paired by nearest neighbour with a 50 ms limit, and **wrote no timestamps to disk**. With a moving camera at 0.1 m/s, 30 ms of error is 3 mm, larger than the accuracy goal.

## Decision
1. **Canonical clock:** `HOST_MONOTONIC` (Linux `CLOCK_MONOTONIC`, ns). `timestamp_ns` in every message is the estimated **mid-exposure** time in this domain.
2. **Record raw values from every clock, decide later.** Per camera frame the recorder stores: host arrival time, RealSense `get_timestamp()` and its domain, metadata `SENSOR_TIMESTAMP`/`FRAME_TIMESTAMP` (µs, device clock) and `ACTUAL_EXPOSURE` when available, and per-stream frame numbers. A host `CLOCK_REALTIME`/`CLOCK_MONOTONIC` pair is sampled at session start and end to convert `RS_GLOBAL` (system-time ms) to host monotonic.
3. **Mapping device to host time** (P1 S4, amended): the primary mid-exposure time is RealSense global time (librealsense's regression of the device clock onto CLOCK_REALTIME at the frame timestamp) converted to HOST_MONOTONIC with the start/end clock pairs, minus `FRAME_TIMESTAMP − SENSOR_TIMESTAMP` (= exposure/2 on the D405) — method `rs_global_sensor`. The lower-envelope fit `t_host = a + b · t_device` of host arrival vs. the device mid-exposure clock is always computed as the cross-check and is the fallback without global time, minus a declared constant latency (`envelope_minus_<L>ns`; without any device clock `arrival_minus_<L>ns`). The method is recorded in `FrameTiming.method`.
   *Why amended:* on the 2026-10-28 sessions the envelope and global time agree in rate (−68 ppm vs −69 ppm wrist) and shape (residual p95 0.08–0.15 ms) but the envelope's offset contains the whole-frame transfer latency, 27–28 ms wrist and 65 ms head. Using the envelope as the timestamp would put every wrist frame ~28 ms late relative to the robot, i.e. ~2.8 mm at 0.1 m/s, with no `dt_robot_cam` to absorb it (decision 7). The live source measures the same 27.8–28.3 ms.
4. **Record every robot sample**, not only paired ones: `robot.jsonl` stores sequence number, host time, joint angles and controller TCP pose for all samples. Pairing is a replay-time function, so the sync algorithm can change without re-recording.
5. **Robot rate:** prefer RealMan UDP real-time state push (target ≥ 100 Hz, to be verified on the installed controller/SDK); fall back to polling (stamp = midpoint of request). The source used is recorded.
6. **Interpolation, not nearest:** `T_base_tcp(t)` = slerp(R) + lerp(t) between the bracketing samples, valid only when the bracket gap ≤ `sync.max_interp_gap_ns` (`configs/sensors.yaml`, currently 31 ms = ceil(p99.9) of 8262 successful robot intervals: p50 10.8, p99 21.0, p99.9 30.3, max 36.0 ms; 4 intervals exceed it). No extrapolation: outside the bracket the frame gets `SyncStatus.GAP_TOO_LARGE` / `OUT_OF_RANGE` and no camera prior. The value is provisional (`configs/provisional_params.yaml`).
7. **Residual camera–robot offset** `dt_robot_cam_ns` stays `0` in `CalibrationBundle`. This rig's reachable viewpoints and speeds cannot separate a time offset from hand-eye error, so the offset is not estimated and is not an I0 pass criterion (2026-10-28). Raw clocks are still stored, so a later session with enough motion can fit it without redefining the contract.
8. **Colour/depth exposure pairing** (added 2026-10-28): librealsense sometimes delivers a frameset whose colour and depth come from different exposures (a repeated colour frame with new depth, or depth a frame interval off): 14–15 % of wrist frames on the dual-camera sessions. A source checks `depth_timing.SENSOR_TIMESTAMP − SENSOR_TIMESTAMP` against the stream's in-sync offset (`rgbd.max_color_depth_dt_ms`) and does not emit such frames; it counts them per reason (`source_meta.rgbd_rejected_before`, `EndOfStream.not_emitted`, sensors report). They are not registered RGB-D, so `T_base_cam_prior` at the colour time would misplace the depth.

## Consequences
V1 sessions lack timestamps and are not reused (ADR-0007); the contracts therefore have no untimed or nearest-neighbour pairing mode. Replay uses bracketing interpolation at `dt_robot_cam_ns = 0`.
